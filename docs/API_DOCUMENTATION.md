## 1. Overview

The Medical Handwriting OCR API is a production-ready FastAPI application that provides end-to-end handwriting recognition for Arabic medical prescriptions and clinical notes. It features dual-engine OCR (PaddleOCR + TrOCR), human-in-the-loop correction workflows, dictionary integration with UMLS/SNOMED validation, DICOM support, and async task processing via Celery.

### Base URL

```
https://your-domain.com
```

| Environment | Base URL |
|---|---|
| Production | `https://ocr-api.hospital.example.com` |
| Staging | `https://staging-ocr-api.hospital.example.com` |
| Development | `http://localhost:8000` |

### API Version

The current API version is **3.0.0**. Version is returned by the `/health` and `/` endpoints.

### Interactive Documentation

| URL | Description |
|---|---|
| `/docs` | Swagger UI — interactive API explorer |
| `/redoc` | ReDoc — alternative documentation viewer |
| `/openapi.json` | OpenAPI 3.0 specification (JSON) |

### Authentication

All protected endpoints require authentication via:

- **`X-API-Key`** header (recommended)
- **`api_key`** query parameter (for testing / webhooks)

See [Section 2 — Authentication](#2-authentication) for full details.

### Rate Limiting Overview

All responses include rate-limit headers:

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Maximum requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp when the window resets |
| `Retry-After` | Seconds until retry is allowed (only on `429` responses) |

Default limits:

| Endpoint Category | Limit |
|---|---|
| Default (most endpoints) | 100 requests/minute per IP |
| Upload (`POST /api/upload`, `POST /api/dicom/upload`) | 20 requests/minute per IP |
| Corrections (`POST /api/correct`) | 60 requests/minute per IP |

See [Section 6 — Rate Limiting](#6-rate-limiting) for full details.

## 2. Authentication

### 2.1 API Key Authentication

API keys are generated by administrators and stored as SHA-256 hashes in the `api_keys` database table. The raw key is never persisted.

#### Creating an API Key

API keys are created directly in the database (no API endpoint exists for self-service creation). An administrator would typically use a script or SQL:

```sql
-- Generate a random key (e.g., mho_live_a1b2c3d4e5f6g7h8)
-- Hash it with SHA-256 and insert:
INSERT INTO api_keys (key_hash, name, description, rate_limit, created_by)
VALUES (
    encode(digest('mho_live_a1b2c3d4e5f6g7h8', 'sha256'), 'hex'),
    'pharmacy-integration',
    'Key for pharmacy department integration',
    50,
    '00000000-0000-0000-0000-000000000001'
);
```

#### Using an API Key

**Via header (recommended):**

```bash
curl -H "X-API-Key: mho_live_a1b2c3d4e5f6g7h8" \
     https://your-domain.com/api/upload
```

**Via query parameter:**

```bash
curl "https://your-domain.com/api/upload?api_key=mho_live_a1b2c3d4e5f6g7h8" \
     -F "file=@prescription.jpg"
```

> **Warning:** Query parameter auth exposes the key in server logs, browser history, and referrer headers. Use header-based auth in production.

#### Key Validation Flow

1. Client sends `X-API-Key` header or `api_key` query parameter.
2. Middleware computes the SHA-256 hash of the raw key.
3. Hash is looked up in the `api_keys` table.
4. The system checks: key exists, `is_active` is `true`, `expires_at` is `NULL` or in the future.
5. Per-key rate limit is enforced (stored in the `rate_limit` column, default: 100/min).
6. The `last_used_at` timestamp is updated.
7. Key metadata is attached to `request.state.api_key` for downstream use.

### 2.2 Admin Bypass

Requests with a valid `X-Admin-Token` header bypass all API key authentication. The admin token is configured via the `ADMIN_TOKEN` environment variable.

```bash
curl -H "X-Admin-Token: your-admin-secret-token" \
     https://your-domain.com/api/deploy/status
```

When admin bypass is used, `request.state.api_key` is set to:
```json
{
  "id": null,
  "name": "admin",
  "is_admin": true
}
```

### 2.3 Bypass Paths

The following paths skip authentication entirely (configurable via `BYPASS_PATHS` environment variable):

| Path | Purpose |
|---|---|
| `/health` | Health checks (load balancers, monitoring) |
| `/docs` | Swagger UI |
| `/openapi.json` | OpenAPI specification |
| `/redoc` | ReDoc viewer |
| `/favicon.ico` | Browser icon |

### 2.4 Disabling Authentication

Set `API_KEY_AUTH_ENABLED=false` (or set `API_KEY_ENABLED=false` in `app/config.py`) to disable API key enforcement for all requests. This is intended for local development only.

### 2.5 Example: Authenticated vs Unauthenticated

**Without auth (will fail on protected endpoints):**

```bash
curl https://your-domain.com/api/pending
# → 401 Unauthorized
# {"error": "Unauthorized", "detail": "API key is required. Provide it via 'X-API-Key' header or 'api_key' query parameter."}
```

**With valid API key:**

```bash
curl -H "X-API-Key: mho_live_a1b2c3d4e5f6g7h8" \
     https://your-domain.com/api/pending
# → 200 OK
# [{"id": "...", "predicted_text": "...", ...}]
```

**With admin token:**

```bash
curl -H "X-Admin-Token: your-admin-secret-token" \
     https://your-domain.com/deploy/status
# → 200 OK
# {"status": "active", "active_version_name": "v2.3.0-FT", ...}
```

  "version_name": "v2.3.0-FT",

### 3.2 Error Responses

All errors follow a structured JSON format. There are four error categories:

#### Validation Errors (422 Unprocessable Entity)

Returned when request body, query parameters, or path parameters fail Pydantic validation.

```json
{
  "error": "validation_error",
  "detail": [
    {
      "field": "body.corrected_text",
      "message": "field required",
      "type": "value_error.missing"
    }
  ],
  "path": "https://your-domain.com/api/correct"
}
```

#### Upload Validation Errors (400 Bad Request)

Returned when file upload fails validation (size, magic bytes, content type, filename).

```json
{
  "error": "validation_error",
  "detail": "File size (15.32 MB) exceeds the maximum allowed size (10 MB)",
  "path": "https://your-domain.com/api/upload"
}
```

#### HTTP Errors (400, 401, 403, 404, 409, 429)

Returned for standard HTTP error conditions.

```json
{
  "error": "Region not found",
  "status_code": 404,
  "path": "https://your-domain.com/api/approve/00000000-0000-0000-0000-000000000000"
}
```

**Authentication errors (401):**

```json
{
  "error": "Unauthorized",
  "detail": "API key is required. Provide it via 'X-API-Key' header or 'api_key' query parameter."
}
```

**Forbidden errors (403):**

```json
{
  "error": "Forbidden",
  "detail": "Invalid, inactive, or expired API key."
}
```

#### Server Errors (500 Internal Server Error)

Returned for unexpected exceptions. Always includes an `error_id` for support correlation.

```json
{
  "error": "internal_server_error",
  "error_id": "a1b2c3d4",
  "message": "An unexpected error occurred. Please try again or contact support.",
  "path": "https://your-domain.com/api/upload"
}
```

> **Reporting server errors:** Include the `error_id` when contacting support. It maps to a specific log entry in the server's structured JSON logs.

### 3.3 Rate Limit Exceeded (429)

Returned when the client exceeds the rate limit for any endpoint.

```json
{
  "error": "Too Many Requests",
  "detail": "Rate limit exceeded. 20 per 1 minute",
  "retry_after": 42
}
```

**Response headers:**

```
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 20
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1719843600
Retry-After: 42
```

### 3.4 Response Headers Summary

Every response may include these headers:

| Header | Type | Present When |
|---|---|---|
| `X-RateLimit-Limit` | `integer` | Always |
| `X-RateLimit-Remaining` | `integer` | Always |
| `X-RateLimit-Reset` | `integer` (Unix timestamp) | Always |
| `Retry-After` | `integer` (seconds) | Only on `429` responses |
| `Content-Disposition` | `string` | File downloads (reports) |

| Code | Description |
|---|---|
| `200` | OCR completed successfully |
| `400` | Validation failed (file too large, wrong type, corrupt image, cannot decode) |
| `401` | API key missing |
| `403` | API key invalid, inactive, or expired |
| `429` | Rate limit exceeded (20/min) |
| `500` | Internal server error |

**Notes & Caveats:**
- Regions with confidence < 0.75 are automatically flagged as `"pending"` for human review.
- Each region's crop image is uploaded to MinIO and accessible via `crop_url`.
- The OCR engine uses PaddleOCR with `ar,en` language configuration.
- Script classification (Arabic vs. English) is performed on each region automatically.
- Files are temporarily stored in `/tmp` during processing and cleaned up afterward.
- Magic byte verification prevents file extension spoofing attacks.

## 6. Rate Limiting

### 6.1 Limits by Endpoint

The API uses SlowAPI with an optional Redis backend for distributed rate limiting. When Redis is unavailable, it falls back to in-memory rate limiting.

| Endpoint Pattern | Limit | Config Variable |
|---|---|---|
| Default (all other endpoints) | 100 requests/minute per IP | `RATE_LIMIT_DEFAULT` |
| `POST /api/upload` | 20 requests/minute per IP | `RATE_LIMIT_UPLOAD` |
| `POST /api/dicom/upload` | 20 requests/minute per IP | `RATE_LIMIT_UPLOAD` |
| `POST /api/correct` | 60 requests/minute per IP | `RATE_LIMIT_CORRECT` |

### 6.2 Per-Key Rate Limiting

In addition to IP-based rate limiting, each API key has its own rate limit stored in the `api_keys.rate_limit` column (default: 100/min). This is enforced at the middleware level and is independent of the IP-based limits.

### 6.3 Response Headers

Every response includes these headers:

| Header | Description | Example |
|---|---|---|
| `X-RateLimit-Limit` | Maximum requests per window | `100` |
| `X-RateLimit-Remaining` | Remaining requests in this window | `73` |
| `X-RateLimit-Reset` | Unix timestamp when the window resets | `1719843600` |

On `429` responses, an additional header is included:

| Header | Description | Example |
|---|---|---|
| `Retry-After` | Seconds until the client may retry | `42` |

### 6.4 Handling Rate Limit Errors

When a `429 Too Many Requests` response is received:

```json
{
  "error": "Too Many Requests",
  "detail": "Rate limit exceeded. 20 per 1 minute",
  "retry_after": 42
}
```

**Recommended client behavior:**

1. Read the `Retry-After` header (or `retry_after` field) to know when to retry.
2. Implement exponential backoff with jitter if `Retry-After` is not available.
3. For batch operations, throttle requests to stay within the limit.

**Example (Python):**

```python
import time
import requests

response = requests.post(url, files=files, headers=headers)
if response.status_code == 429:
    retry_after = int(response.headers.get("Retry-After", 60))
    time.sleep(retry_after)
    # Retry the request
```

### 6.5 Rate Limiting Configuration

| Environment Variable | Default | Description |
|---|---|---|
| `RATE_LIMIT_DEFAULT` | `"100/minute"` | Default requests per minute for all endpoints |
| `RATE_LIMIT_UPLOAD` | `"20/minute"` | Rate limit for upload endpoints |
| `RATE_LIMIT_CORRECT` | `"60/minute"` | Rate limit for correction endpoints |
| `REDIS_URL` | `"redis://localhost:6379/2"` | Redis URL for distributed rate limiting |
| `REDIS_RATE_LIMIT_URL` | `null` (falls back to `REDIS_URL`) | Dedicated Redis DB for rate limiting |

The rate limiter uses a **fixed-window elastic-expiry** strategy. This means:
- The time window resets at fixed minute boundaries.
- When a request is rate-limited, the window expiry is extended elastically.

## 8. SDK Examples

### 8.1 Python (requests)

```python
import requests

BASE_URL = "https://your-domain.com"
API_KEY = "mho_live_a1b2c3d4e5f6g7h8"
HEADERS = {"X-API-Key": API_KEY}


# ── Upload a prescription image ──
def upload_prescription(image_path: str, user_id: str = "anonymous") -> dict:
    """Upload a prescription image and run OCR."""
    with open(image_path, "rb") as f:
        response = requests.post(
            f"{BASE_URL}/api/upload",
            headers=HEADERS,
            files={"file": f},
            data={"user_id": user_id},
        )
    response.raise_for_status()
    return response.json()


# ── Get pending corrections ──
def get_pending(limit: int = 50) -> list:
    """Fetch regions that need human review."""
    response = requests.get(
        f"{BASE_URL}/api/pending",
        headers=HEADERS,
        params={"limit": limit},
    )
    response.raise_for_status()
    return response.json()


# ── Submit a correction ──
def submit_correction(region_id: str, corrected_text: str, user_id: str = "anonymous") -> dict:
    """Correct an OCR-recognized text region."""
    response = requests.post(
        f"{BASE_URL}/api/correct",
        headers={**HEADERS, "Content-Type": "application/json"},
        json={
            "region_id": region_id,
            "corrected_text": corrected_text,
            "user_id": user_id,
        },
    )
    response.raise_for_status()
    return response.json()


# ── Approve a correction ──
def approve_region(region_id: str, reviewer_id: str = "system") -> dict:
    """Promote a corrected region to gold standard."""
    response = requests.post(
        f"{BASE_URL}/api/approve/{region_id}",
        headers=HEADERS,
        params={"reviewer_id": reviewer_id},
    )
    response.raise_for_status()
    return response.json()


# ── Get suggestions ──
def get_suggestions(text: str, is_medical: bool = False) -> dict:
    """Get correction suggestions for OCR text."""
    response = requests.get(
        f"{BASE_URL}/suggestions/",
        headers=HEADERS,
        params={"text": text, "is_medical": is_medical},
    )
    response.raise_for_status()
    return response.json()


# ── Upload DICOM file ──
def upload_dicom(dicom_path: str, user_id: str = "anonymous") -> dict:
    """Upload and parse a DICOM medical imaging file."""
    with open(dicom_path, "rb") as f:
        response = requests.post(
            f"{BASE_URL}/api/dicom/upload",
            headers=HEADERS,
            files={"file": f},
            data={"user_id": user_id},
        )
    response.raise_for_status()
    return response.json()


# ── Generate a report ──
def generate_report(days: int = 30, format: str = "pdf", output_path: str = "report.pdf") -> None:
    """Download a performance report."""
    response = requests.get(
        f"{BASE_URL}/api/reports/generate",
        headers=HEADERS,
        params={"days": days, "format": format},
    )
    response.raise_for_status()
    with open(output_path, "wb") as f:
        f.write(response.content)


# ── Check deployment status ──
def get_deployment_status() -> dict:
    """Check the currently active model version."""
    response = requests.get(
        f"{BASE_URL}/deploy/status",
        headers=HEADERS,
    )
    response.raise_for_status()
    return response.json()


# ── Full workflow example ──
if __name__ == "__main__":
    # 1. Upload a prescription
    result = upload_prescription("prescription_001.jpg", user_id="dr_ahmed")
    doc_id = result["document_id"]
    print(f"Uploaded document: {doc_id}")

    # 2. Check pending corrections
    pending = get_pending(limit=10)
    print(f"Pending corrections: {len(pending)}")

    # 3. Get suggestions for the first pending region
    if pending:
        region = pending[0]
        suggestions = get_suggestions(region["predicted_text"], is_medical=True)
        print(f"Suggestions: {suggestions['suggestions_count']}")

        # 4. Submit correction using the best suggestion
        if suggestions["suggestions"]:
            best = suggestions["suggestions"][0]["text"]
            correction = submit_correction(
                str(region["id"]),
                best,
                user_id="dr_ahmed",
            )
            print(f"Corrected: {correction['previous_text']} → {correction['corrected_text']}")

            # 5. Approve the correction
            approve_region(str(region["id"]), reviewer_id="dr_khalid")
            print("Approved as gold standard")

    # 6. Generate a report
    generate_report(days=30, format="pdf", output_path="monthly_report.pdf")
    print("Report generated: monthly_report.pdf")
```
